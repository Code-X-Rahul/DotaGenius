**BullMQ queue** (`src/lib/queue.ts`):
- Define `ReplayJobData` interface: `{ matchId: string }`
- Create and export `replayQueue` with name 'replay-pipeline'
- Default job options: 3 attempts, exponential backoff (5000ms), removeOnComplete after 24h, removeOnFail after 7d
- Use `redisConnection` from `src/lib/redis.ts`

**Worker** (`src/workers/replay-worker.ts`):
This runs as a SEPARATE process (not inside Next.js). Create a standalone script:
1. Import redisConnection, prisma, getMatch, parseReplay, constructReplayUrl, and optionally getReplaySalt (check 01-02-SUMMARY.md for GC spike result)
2. Create Worker for 'replay-pipeline' queue with concurrency: 2
3. Job processing flow:
   a. Update progress: `{ stage: 'downloading', percent: 0 }`
   b. Call `getMatch(matchId)` from OpenDota
   c. Create/update Match record in DB with status 'downloading', store match metadata (duration, startTime, gameMode, radiantWin, cluster)
   d. Determine replay URL:
      - If OpenDota response has `replay_url`: use it
      - Else if GC is available: call `getReplaySalt(matchId)`, construct URL
      - Else: throw error "Replay URL not available"
   e. Update progress: `{ stage: 'parsing', percent: 30 }`
   f. Call `parseReplay(replayUrl)`
   g. Update Match record status to 'parsing'
   h. Update progress: `{ stage: 'storing', percent: 60 }`
   i. Process parsed events and store in PostgreSQL using Prisma transactions:
      - Extract player stats from events and upsert Player records
      - Filter combat_log events and batch insert CombatLogEvent records
      - Filter position/interval events (every 10 seconds) and batch insert PositionSnapshot records
      - Use `prisma.$transaction()` for atomicity
   j. Update Match record: status 'complete', parsedAt = now(), replayUrl
   k. Update progress: `{ stage: 'complete', percent: 100 }`
4. Error handling: catch errors, update Match status to 'failed' with errorMsg, rethrow for BullMQ retry
5. Add the cleanup repeatable job on worker startup (every 6 hours, cleanup .dem files older than 24 hours -- though with /blob endpoint this may be a no-op)

**API endpoint** (`src/app/api/matches/[matchId]/route.ts`):
- `POST`: Validate matchId with zod schema. Check if match already exists in DB (if complete, return cached result with 200). If not, add job to replayQueue with matchId as job ID (prevents duplicates). Return 202 with `{ jobId, matchId, status: 'queued' }`.
- `GET`: Look up match in DB by matchId. If found and complete, return match data with players. If found but not complete, return current status. If not found, return 404.

Note on parsed event processing: The exact event types from odota/parser are documented in the research as needing validation. The worker should handle common event types:
- Events with `type: "combat_log"` -> CombatLogEvent table
- Events with `type: "interval"` that contain hero position/gold/xp data -> PositionSnapshot table (filter to every 10 seconds)
- Events with `type: "epilogue"` or player-summary data -> Player table
Log and skip unknown event types rather than crashing.
